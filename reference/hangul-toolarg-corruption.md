# 도구 호출 인자의 한글은 조용히 손상될 수 있다

**모든 도구 호출 인자(tool arguments)가 대상이다.** 특정 도구의 문제가 아니고, 인자 구조(평평한 문자열 / 중첩 배열-객체)와도 무관하다. `Write.content`, `Edit.new_string`, `Bash.description`, `Agent.prompt`, `AskUserQuestion`의 질문·선택지, 그리고 Notion·Linear·Slack 같은 MCP 서버의 본문 인자를 **예외 없이 같은 위험군으로 취급한다.**

## 증상 — 적법한 한글 음절로 바뀌어 있다

깨진 결과가 여전히 정상적인 한글 음절이라는 점이 핵심이다. 파일은 UTF-8로 멀쩡하고 JSON도 완전해서, 눈으로 읽지 않으면 드러나지 않는다.

| 의도한 말 | 실제로 나간 것 |
|---|---|
| 파라미터 / 대비 / 채택 | `파라밌터` `대별` `채필` |
| 추출 / 맞춰 / 형태 | `추천` `맞춴` `형토` |
| 갱신 / 평균 / 계층 | `갱슱` `평군` `계습` |
| 엉뚱한 / 벗겨내는 / 커지고 | `엉둥한` `벗겼내는` `촌하고` |
| 요청 / 산출물 / 하겠습니다 | `요정` `산증물` `하게습니다` |
| 겹치니 / 규정상 / 가깝지만 | `곹치니` `귬정상` `가깜지만` |
| 통째 / 긁어 | `통챠` `긍어` |

주로 **음차 기술어**(파라미터·코퍼스·세그먼트)와 **한자어**(추출·갱신·계층·평균)에서 한 음절만 어긋난다. 드물게는 단어 사이에 공백이 끼어들거나(`밑 을 이 준 없음`), 한글 자모 채움문자(U+115F 등)가 섞이거나, 필수 필드가 빈 문자열로 전송되기도 한다. 한 사례에서는 긴 한글 본문 6,000자에 13곳이 깨져 있었다 — **분량이 길수록 늘어난다.**

## 원인 — JSON 인자를 유니코드 이스케이프로 쓰다 16진수가 틀린다

도구 호출 인자는 JSON으로 생성되고, 그 안에서 한글이 `\uXXXX` 유니코드 이스케이프로 쓰인다. 음절마다 16진수 4자리를 정확히 뽑아야 하는데 한 자리만 어긋나도 **다른 적법한 한글 음절**이 나온다 — U+AC00–D7A3 구간이 촘촘히 채워져 있어 대부분의 오타가 유효한 음절로 착지한다. 그래서 오류가 오류처럼 보이지 않는다. 같은 이슈가 gpt-oss 계열 모델에서도 보고된 이력이 있다.

**핵심 함정: 이스케이프로 썼다는 사실을 사후에 확인할 수 없다.** 하니스가 JSON을 파싱할 때 이스케이프는 문자로 디코딩되고, 트랜스크립트·모델 자신의 컨텍스트·훅이 받는 `tool_input`에는 **그 결과 문자만** 돌아온다. 따라서 하류에서 리터럴 이스케이프가 보이지 않는다는 것은 이스케이프를 쓰지 않았다는 증거가 되지 못한다.

긍정 증거는 드물게 **깨진 채로 새어 나오는 이스케이프**다. 관측된 예: 한 인자가 `\u洞\uchㅊ\uc튼`(의도: 규칙)으로 도착했다. 16진수가 놓일 자리에 한글·한자가 들어앉은 형태다. `이번ᅟ`처럼 U+115F(한글 초성 채움문자)가 섞이는 것도 같은 방향을 가리킨다 — 타이핑으로는 나올 수 없고 잘못 인코딩될 때만 나오는 코드포인트다.

산문은 깨끗한데 인자만 깨지는 비대칭도 이것으로 설명된다: 산문은 평문 토큰으로 나가고, 인자는 JSON 이스케이프 경로를 탄다.

두 가지 결론:

- **인자의 한글을 raw UTF-8로 쓰라는 지시는 방향이 맞지만 검증이 불가능하다.** 모델도 훅도 준수 여부를 확인할 수 없으므로 이것만 믿어서는 안 된다.
- **구문 검사 훅은 실효가 없다.** 훅은 디코드 **하류**에 있어 검사할 대상이 도달하지 않는다. "인자에 유니코드 금지" 류를 만들려 하지 말 것. 자동 탐지에는 한국어 사전이나 형태소 분석기가 필요하다.

## 실효가 있는 대응: 되읽기

**생성은 손상되지만 인식은 정상이다** — 위 표의 사례는 모두 기록을 *읽어서* 찾아낸 것이다. 그러므로 예방이 아니라 검출로 대응한다.

- 한글 본문을 외부·영속 목적지로 보낸 **직후 되읽어 확인한다**: Notion·Linear·Slack 등 MCP 쓰기, 파일 Write/Edit, 커밋 메시지, `AskUserQuestion` 선택지.
- 가장 위험한 것은 **사용자가 착지 전에 볼 수 없는 긴 한글 본문**이다. 로컬 파일은 사용자가 diff로 보지만, 외부 서비스로 published된 본문은 아무도 안 본 채 남는다.
- 훑는 방법: 비단어를 찾는다. 음차 기술어와 한자어에서 한 음절만 어긋난 형태를 특히 본다.
- 발견하면 **조용히 고쳐 덮어쓰지 말고 사용자에게 알린다.** 이미 발행된 문서는 교정 대상이고, 사용자가 알아야 할 사실이다.
- **한글을 피하는 우회를 기본값으로 삼지 않는다.** 영어로 바꾸거나 인자의 한글 분량을 줄이는 것은 문제를 옮기는 것이다. 한글로 쓰되 검증한다.

*근거: 2026년 7월, 한 사용자의 Claude Code 세션 로그 전량(398개 세션 267MB)에서 손상 사례를 손으로 검증해 정리했다. 근본적으로는 디코딩/서빙 레이어의 결함으로 보이며, 이 문서는 그 층을 고치는 것이 아니라 손상을 검출하기 위한 것이다.*
